Overview

This specification tells the developer what the Super Admin portal must do, in what order to build it, and which rules must hold across every screen. It extends the working FastAPI + React + MySQL app (students, institutes, wallet, commission ledger, settlements are already built).

Version 1 boundary. Only AP EAPCET Engineering (MPC) question generation is live in version 1, in English with Telugu as a safe fallback. The institute profile, syllabus board, language and training-type data are stored from day one, but other exams (UPSC, NEET, CAT and so on) are shown as "coming soon" until their generation is built.

How to read each feature. Every feature has a status tag, a phase tag, and a "Done when" line the developer can test against.

Tag Meaning
Built Already working in the current code. Only the listed change is new.
New Not in the code yet.
P1 to P4 Build phase from section 13. P1 = safety, P2 = daily operations, P3 = quality, P4 = growth.

What changed from v3.

  • Added a decisions section, a role-by-feature matrix, one exam-eligibility rule, a background-jobs section and a compliance checklist.
  • The bulk import now includes value mapping, duplicate handling, password handling, undo and file limits.
  • Chat leftovers, stale cross-references and typos were removed, and the build order now covers every feature.

Rules

Exam eligibility rule

A student can start an exam only when every check below passes, evaluated in this order by one server function (for example can_start_exam(student)) that every screen and API calls. The first failing check decides the message. Direct students skip the institute checks.

Order Check If it fails Message shown
1 Platform maintenance mode is off Block everyone except Super Admin "The platform is under maintenance. Please try again later."
2 Student status is Active (not Blocked or Archived) Block login and exams "Your account is not active. Please contact your institute."
3 Institute is Active (not Deactivated) Block login, delete all its sessions "Your institute is currently deactivated."
4 Institute onboarding status is Trial or Active (not Suspended) Login allowed, results viewable, no new exams "New exams are paused for your institute."
5 Today is inside the institute contract window Before start: no new exams. After end: treated as Suspended "Your institute's access is not active right now."
6 Student exam permission is On No new exams "You are not permitted to take exams. Please contact your institute."
7 No exam already in progress Send the student to resume it "You already have an exam in progress."
8 Wallet balance is at least the effective price No charge, no exam "Please load the wallet."
9 A question set is ready No charge, no exam "We couldn't prepare your paper. Your wallet was not charged."

Deactivated versus Suspended. Deactivated is a hard stop: nobody from that institute can log in. Suspended is a soft stop: students can still log in and read past results, but cannot start new exams; use it for overdue payment, an expired contract or an investigation. Historical reports and pending settlements stay intact in both.

The student limit is not an exam check. It is enforced when a student is added, imported, restored from archive or transferred in, and counts only Active students.

Done when

one function holds these rules, every entry point calls it, and a test covers each row of the table.

Section 1

Access and security

Admin access is protected by a password plus an email one-time code, throttled against guessing, split into roles, and recorded in a permanent audit log.

1.1

Admin login and logout with email OTP

Built: login, session; New: OTP

BuiltNewP1
  1. The admin signs in at /exam/admin with username and password. If correct, the server emails a 6-digit OTP to the admin's registered address and creates no session yet.
  2. The admin enters the OTP. It is valid for 5 minutes, usable once, and locked after 5 wrong attempts. Only then does the server create the session token.
  3. Logout deletes the token from the sessions table at once.
Developer notes
  • Add an email column to admins (migration m004) and an admin_otps table: admin_id, otp_hash, expires_at, attempts, used.
  • Store only a hash of the OTP. Allow a resend every 60 seconds, with a cap per hour.
  • Send mail through cPanel SMTP; keep host, user and password in the .env file outside public_html.
  • The API has two steps: POST /api/admin/login returns a temporary "otp_required" token, then POST /api/admin/verify-otp returns the session token. Show the email masked, for example a****@gmail.com.
  • Session length follows decision 5 (2-hour idle timeout, 12-hour maximum).
  • Recovery: keep a second Owner account or one-time backup codes so a mail failure never locks everyone out. Test live mail delivery before enabling.
Done when

a correct password alone never opens the portal, an expired or reused OTP is rejected, and logout makes the old token fail on the next request.

1.2

Login throttling, lockout and password rule

NewP1
  • After 5 wrong attempts, lock that username for 15 minutes and also block that IP address for the same time. A correct login resets the counter. Failed attempts are stored per username and per IP.
  • Always show the same message, "Invalid username or password", so an attacker cannot tell whether a username exists.
  • Optionally email the admin when a lockout happens.
  • Password rule for admins: at least 10 characters with letters and numbers, not on a common-password list (for example admin@123, 123456, password). Institutes and students: at least 8 characters, with a softer limit of 10 failed attempts.
  • Force a password change at first login so a default password never stays in use.
Done when

the sixth wrong attempt in a row is refused even with the right password, and a weak password is rejected on create and on change.

1.3

Multiple admin accounts with roles

NewP2
  • Each team member has their own username, password and email OTP. Roles are Owner, Finance, Content reviewer and Support; what each can do is in the permission matrix.
  • Add role and is_active to admins, a server-side check on every admin route, and a "Team" screen where only an Owner adds, edits, disables and resets admins.
  • Offboarding is disabling the account; the Owner password is never shared.
Done when

a Support user calling a settlement endpoint gets 403, and the last active Owner cannot be disabled or demoted.

1.4

Audit log

NewP1
  • Every important change writes one row, in the same database transaction as the change, so it cannot be skipped. Table audit_log: id, admin_id, admin name, role, action (for example price.update), target type and id, old value and new value (JSON), IP address, time.
  • Covered actions: prices, commission, settlements and reversals, student and institute edits, password resets, blocks, wallet adjustments, refunds and voids, regrades, lesson approvals, imports, exports of student data, forced logouts, and every admin login, failed login and logout.
  • The table is append-only: the application has no edit or delete for it.
  • An "Audit log" screen for the Owner with filters by person, action and date, and an Excel export.
Done when

changing a commission rate shows who, when, the old rate and the new rate, and no screen can edit or remove a log row.

1.5

Two-factor login and forced logout

Built: some session deletion; New: screen

BuiltNewP1P2
  • Two-factor login (1.1) applies to every admin account first; an authenticator app can replace email later.
  • A "Sessions" screen lists active sessions: user, role, login time, IP, device. Buttons: log out this session, log out all sessions of a user, and log out everyone (emergency, Owner only).
  • Each action deletes the matching sessions rows and writes an audit entry. The user's next request gets "Session expired".
  • Use it when a password leaks, an institute stops paying, or a team member leaves.
Done when

after a forced logout the user's next request returns to the login page, and the action appears in the audit log.

1.6

Forgot password for institutes and students

NewP2

Institutes and students can reset their own password with an emailed link or OTP, with the same throttling and password rule as 1.2. Admin-initiated reset stays available (3.5).

Done when

a reset link works once, expires, and signs out the account's old sessions.

Section 2

Manage institutes

The Super Admin creates each coaching institute, sets its commercial terms, records its profile, and controls whether its students can take exams.

2.1

Create and edit an institute, first-login reset, agreement gate, deactivate

Built: create, edit, reset, deactivate; New: the rest

BuiltNewP1P2
  • Create and edit. Name, login username, password and status. Editing never changes past exams, ledgers or settlements.
  • First-login password reset. A checkbox on the create form, "Require password reset on first login", sets must_change_password = true. The institute cannot reach its dashboard until it sets a new password that follows the password rule; the flag then becomes false.
  • Terms, privacy and agreement gate. After login, and after any forced password reset, the dashboard stays blocked until the institute accepts the current Terms & Conditions, Privacy Policy and Institute Agreement. Store the proof: institute id, actor, document version, time and IP address. Prompt again whenever a newer version is published in System Settings (10.2).
  • Confirmation email. On acceptance, send the institute's registered email the accepted versions, the time and a copy or link of the terms. A delayed email must never block dashboard access.
  • Admin password reset. The Super Admin can reset an institute password at any time, optionally forcing a change at next login.
  • Activate or deactivate. Deactivating blocks login and deletes every session token for the institute and all its students, so they are logged out on their next request.
Done when

an institute with the first-login box ticked cannot open any dashboard page before changing its password and accepting the terms, and deactivation logs its students out immediately.

2.2

Per-institute exam prices and commission overrides

BuiltP1
  • Prices. The platform has default prices for Basic, Intermediate and Advanced. An institute may have its own price per level; a blank or cleared price falls back to the platform default.
  • Commission. The platform has a default rule (percent of the fee, or a fixed rupee amount, never more than the fee). An institute may override mode and rate per level.
  • Order of calculation. First resolve the effective fee (institute price, else default), then apply the institute's commission rule. Coupons and promotional credit follow decision 2 in section 5.
  • Snapshots. Store the effective price and the calculated commission on the exam record when the student is charged, so later edits never rewrite history.
Done when

changing an institute's price or commission changes only exams started afterwards.

2.3

Institute profile and payout details

NewP2

One profile record holds everything operations, finance and the AI prompt need.

  • Fields: contact person, phone, email, GSTIN, PAN, registered address, bank account (holder name, account number, IFSC) and UPI ID.
  • Validation: GSTIN 15 characters and PAN 10 characters in the official patterns, IFSC 11 characters, phone and email format.
  • Protection: bank and UPI details are encrypted at rest and visible only to Owner and Finance, with the account number masked on screen. Every change is audited, and a changed bank account needs a second confirmation (Owner or Finance, different person) before the next payout is recorded to it.
Done when

a Support or Content reviewer account cannot see or fetch bank details, and a bank change appears in the audit log with old and new values masked.

2.4

Type of institute, three-level selection

NewP3

Three dependent multi-select lists, stored per institute and driven by editable reference tables (managed in the Syllabus Manager, 6.4) rather than hardcoded lists.

  • Level 1, type of training (multi-select, so a multi-track institute can choose several): (1) Government and public sector job exams: civil services (UPSC, State PSCs such as APPSC/TSPSC), central staff (SSC), banking and insurance (IBPS, SBI, RBI, LIC, NIACL), railways (RRB), defence and paramilitary (NDA, CDS, AFCAT, CAPF, Agniveer), PSU recruitment (GATE or PSU direct exams). (2) Higher education entrance exams: engineering and technology (JEE Main and Advanced, BITSAT, VITEEE, state CETs such as AP/TG EAPCET, MHT CET, KCET, GATE), medical and healthcare (NEET-UG, NEET-PG, INI-CET), management (CAT, XAT, SNAP, NMAT, CMAT, MAT), law (CLAT, AILET, SLAT), central and state universities (CUET-UG, CUET-PG), design, architecture and fashion (NATA, JEE Main Paper 2, NID DAT, NIFT, UCEED, CEED). (3) Eligibility, teaching and professional certification: teaching and research (UGC NET, CSIR NET, CTET, state TETs), professional licences (CA, CS, CMA, AIBE), study abroad (GRE, GMAT, IELTS, TOEFL, PTE). (4) Custom or other.
  • Level 2, related exams: a multi-select filtered by Level 1, plus a custom entry.
  • Level 3, subjects and concepts: a multi-select filtered by Level 2 (for example Civil Services shows Polity and Constitution, Indian Economy, History and Culture, Geography, Environment and Ecology, Science and Technology, Current Affairs, CSAT/Aptitude), plus optional custom concept tags.
  • Custom entries are visible only to that institute until the Owner approves them into the shared list.
  • Institute portal: the dashboard highlights and filters by the institute's saved subjects and concepts.
  • Version 1 boundary: only AP EAPCET Engineering (MPC) can generate exams; other choices are saved and shown as "coming soon".
Done when

choosing a Level 1 option changes the Level 2 choices, the selection is saved and reloaded per institute, and the institute dashboard filters to it.

2.5

Language and syllabus basis

NewP3
  • Language preference: English, Telugu, or both, with a safe fallback to English whenever a Telugu translation is missing.
  • Syllabus or curriculum basis: State, CBSE, NCERT or Other, asked after the training type, exams and subjects are chosen, with an optional override per exam or per subject.
  • Use in AI prompts: training type, related exams, subjects, syllabus board and language are passed as structured inputs that set exam style and depth, syllabus guardrails and the output language for generated questions.
Done when

changing an institute's language or board changes the prompt inputs recorded on its next generated paper.

2.6

Student limit or plan, and contract dates

NewP2
  • Plan and student limit. A cap on Active students per institute, for example Pilot or Trial, Standard, Unlimited. Plan values are set by the Owner; the numbers must match the pilot size agreed in the business plan.
  • Where it is enforced: adding one student, bulk import (flag or block the excess rows during validation), moving a student into an institute, and restoring an archived student. Only Active students count, so archiving frees seats without deleting exam history.
  • Contract dates. A start date and an end date. Before the start date the institute can be set up but exams stay paused. Show contracts expiring in 30 and 7 days on the dashboard. When the end date passes, mark the contract expired and move the institute to Suspended automatically, keeping history and pending settlements.
Done when

the 481st student of a 480-seat plan is refused with "Student limit reached for this plan", and a contract that ends today suspends the institute at midnight.

2.8

Manage Syllabus: lessons, PDFs and approval

NewP3

The add-on that supplies lesson PDFs to ground AI question generation. It is used from two places: the Super Admin portal, where the admin picks an institute from a dropdown, and the Institute portal, where the logged-in institute's own profile and subjects load automatically and everything is scoped to its institute_id.

  • The screen opens with the saved profile context: training type, selected exams, syllabus board, language and subjects.
  • For each selected subject (for example Maths) there are repeatable rows with the name of the lesson and a PDF upload, plus a "+" button to add another pair.
  • Approval states: pending_approval, approved, rejected. Uploads by the Super Admin are approved immediately. Uploads by an institute, and edits or PDF replacements of approved lessons, start as pending_approval.
  • Previous version stays live. When an approved lesson is edited or replaced, the old approved version keeps serving AI generation and live tests until the new version is approved.
  • Review. The approver (decision 6) sees a pending queue with filters, and must enter a reason when rejecting; the reason is visible to the institute. Every action is written to the audit log.
  • PDF handling. Accept PDF only, with a size limit (suggested 25 MB), scan for malware, and store outside public_html with access through authenticated download only. Scanned or image-only PDFs need OCR, and Telugu PDFs often extract as unreadable text, so check extraction quality before approval. Institutes confirm they own or may use the material.
Done when

an institute upload cannot reach AI generation until approved, a rejected lesson shows its reason to the institute, and replacing an approved PDF keeps the old one serving until the replacement is approved.

Section 3

Students (institute and direct)

Students belong either to an institute or to the platform directly (institute_id is empty). The Super Admin manages both; an institute manages only its own.

3.1

Add and edit students

Built; New: contact fields and status

BuiltNewP1P2
  • Fields: full name, username (login ID), class, optional batch or notes, email, phone, exam permission, and the starting assignment (Direct or a specific institute). Email, phone and batch are new columns and need a migration.
  • Add a lifecycle status with Active, Blocked and Archived (3.6).
  • Validation: required fields, valid email and phone, and scoped username uniqueness (3.7). Editing never erases exam history, scores or wallet and ledger records.
Done when

a duplicate username in the same institute is refused with a clear message instead of a database error, and an edit leaves past exams unchanged.

3.2

Exam permission

BuiltP1

A per-student switch. Turning it off blocks starting new exams at once even if the account is active and has wallet balance; turning it on restores eligibility, subject to the rest of the eligibility rule. Use it for fee holds, batch control or a temporary restriction.

Done when

the switch is checked by the single eligibility function and nowhere else.

3.3

Move a student between Direct and an institute, or between institutes

Built: Direct and institute; New: checks

BuiltNewP2
  • Supported moves: Direct to Institute, Institute to Direct, Institute A to Institute B.
  • Checks before the move: the target institute's Active-student limit, a username clash in the target institute (block, or ask for a new username), and no exam in progress for the student.
  • History stays as it was: past attempts, scores, and commission and settlement attribution remain with the institute that earned them. The wallet balance stays with the student. Future exams use the new institute's prices and commission.
  • The student is logged out after the move so the new account type applies.
Done when

a move into a full institute is refused, and the old institute's earnings ledger is unchanged afterwards.

3.4

Bulk import through a staging table and field mapper

NewP2

Excel and CSV headers rarely match database fields ("Student Name" in the file, full_name in the table), so a file never goes straight into students. It is loaded into a staging table, columns are mapped, rows are checked, and only then are valid rows moved to the real table. This follows the ServiceNow Import Set and Transform Map pattern.

Who can use it. Admin screen: choose Direct or a target institute, and download a standard template. Institute screen: locked to the logged-in institute's own institute_id, so it can neither choose another institute nor exceed its student limit. An institute cannot import wallet balance or institute id.

  1. Upload. Accept .csv or .xlsx (UTF-8, so Telugu names work) up to 5 MB and 5,000 rows. Parse it and write every raw row to staging under a new import batch; nothing touches students. Keep the original headers and values so users can re-map without uploading again.
  2. Map fields. For each target field (name, username, email, phone, class, batch, exam permission) choose the source column from a dropdown, or mark a column Ignored. Auto-suggest by case-insensitive name and aliases (for example name, student name and candidate suggest full name). Mapping can be saved as a named template per institute and reused.
  3. Transform and validate. For each mapped field the user may set a default value for every row, a trim or case change, a date format, or a value map (see the example below). Then check every staging row for required fields, email and phone format, a duplicate username inside the file, a duplicate against existing students in that scope, and the institute student limit. Each row is shown as Ready, Warning or Error with a message, and the user can fix, skip, or download an error file.
  4. Commit. Only after confirmation, move valid rows to students inside one database transaction. Record totals (rows, imported, updated, skipped, failed) and write an audit entry with actor, role, scope, batch id and counts.
File column Target field Transform
Student Name full_name Trim, title case
Login ID username Trim, lowercase
Mobile phone Digits only, 10 characters
Class class_name Value map: "1st year", "I Year", "Inter 1" become "Intermediate 1st Year"
(none) exam_permission Default: On

Duplicates and passwords (decision 7). On a username that already exists in the scope the user chooses Skip (default), Update existing, or Error. Passwords may come from a file column or be generated; generated passwords are shown once in a downloadable credentials file, hashed on commit, never stored in plain text in staging, and the student must change it at first login (must_change_password).

Undo and history. An import batch can be undone, which removes the students it created only if none has taken an exam. A batch history lists who uploaded what and when, row counts and status. Staging rows and the stored file are purged after 30 days.

One engine, many targets. Build the import as a generic engine with a registry of target fields, so the same screens later import institutes and questions into the question bank.

Done when

a file with different headers imports correctly through a saved mapping, an over-limit batch is flagged before any row is written, and undoing a batch with no exams removes exactly its students.

3.5

Search, filter and pagination

NewP2
  • Search by name, username, email or phone (and batch or roll number), debounced by 300 to 400 ms, run on the server over indexed columns. On the institute portal results are always restricted to that institute; on the admin portal they cover all students or the chosen filter.
  • Filters: Direct, a specific institute, or all (admin only); status Active, Blocked or Archived; exam permission On or Off; optional batch, password-reset-required, and created date range; a Clear button.
  • Pagination and sorting: page sizes 20, 50 and 100 with a range indicator ("Showing 1 to 50 of 640 students"); sort by name, username, institute, status or created date with id as the tie-breaker; return to page 1 whenever search or filters change.
Done when

a list of 10,000 students loads one page at a time and the institute portal can never return another institute's student.

3.6

Reset password, block or unblock, archive, delete

Built: reset; New: the rest

BuiltNewP2
  • Reset password (Owner, Support, or a scoped institute): set a new password under the password rule or generate a temporary one with a forced change at next login. Delete the student's sessions immediately.
  • Block or unblock: a blocked account cannot log in or start exams, and its sessions are revoked. History is kept. Unblocking restores access, subject to the eligibility rule.
  • Archive (recommended default): moves graduated or inactive students out of active use without deleting data. Archived students do not count toward the student limit; restoring one is allowed only if capacity remains.
  • Delete (Owner only): hard delete is blocked when the student has exam, wallet or commission records. For erasure requests use Anonymize: replace name, username, email and phone with neutral values while keeping scores and ledger totals for accounting.
Done when

Support cannot delete or anonymize, a blocked student's next request is rejected, and an archived student frees one seat.

3.7

Username unique per institute

NewP1
  • The rule is unique within institute_id plus the normalized username (trimmed and lowercased, so "Rahul" and "rahul" are the same). Two institutes may both have student01. Direct students are unique within the direct pool.
  • MySQL does not enforce uniqueness when institute_id is empty, so add a generated column such as scope_key = COALESCE(institute_id, 0) and a unique index on (scope_key, username_normalized). The migration drops the current global unique index on username.
  • Enforce it on add, edit, import and transfer with a clear message, never a raw database error.
  • Login. The student login resolves the account by institute context (the selected institute, or Direct) plus username. This is already partly in the login screen and must be applied in the lookup.
Done when

two institutes each create rahul without error, and a student logs into the right one by choosing the institute.

4
Section 4

Pricing and wallet

Students pay from a wallet. Exam fees come from default or per-institute prices; money moves only through server-checked, logged transactions.

4.1

Default and per-institute prices

Built; New: price history

BuiltNewP1
  • One central price list for Basic, Intermediate and Advanced, with effective-from timestamps and a change history in the audit log.
  • An institute override applies when set; a blank override falls back to the default.
  • The resolved price is stored on every exam record at the moment of charge, so later price edits never alter past transactions or reports.
Done when

changing a default price changes only exams started after the change, and the old and new prices are in the audit log.

4.2

Coupons, promo codes and free trial credits

NewP4
  • Coupons: percentage or fixed discount, start and expiry dates, total usage limit, per-student limit, minimum order value, and a scope (all students, Direct only, a specific institute, or a specific exam level).
  • Redemption is validated on the server inside a database transaction, so two simultaneous requests cannot exceed a usage cap. The applied code and discount are stored on the exam record.
  • Free trial credits can be given to new direct students or trial institutes. They are a separate promotional bucket in the wallet ledger, with an optional expiry date, and are never withdrawable. By default an exam draws promotional credit first because it expires.
  • Who bears a discount, and whether commission is earned on promotional credit, follow decisions 2 and 3.
Done when

a coupon with a limit of 10 cannot be redeemed an eleventh time under concurrent requests, and the wallet shows paid balance and promotional balance separately.

4.3

Manual wallet credit or debit by an admin

NewP2
  • Owner and Finance can credit or debit a student's wallet for goodwill, offline cash or bank receipts, or error corrections, with a mandatory reason and a reference id.
  • A manual debit can never take the balance below zero.
  • Update the balance and append an immutable wallet_ledger row in the same transaction, and write old balance, new balance and reason to the audit log.
Done when

a debit larger than the balance is refused, and every manual change shows the admin's name and reason.

4.4

Refund exam

NewP2
  • One action, for failed generations, voided exams or approved disputes, that credits the exact snapshotted amount back to the student's wallet and reverses the matching institute commission in the same transaction. Each part returns to the bucket it came from (paid or promotional).
  • Mark the exam as refunded so it cannot be refunded twice. Full and partial refunds are supported; a partial refund creates a matching credit note (5.5).
  • If the commission was already paid out in a settlement, record a negative adjustment (clawback) in the institute ledger so the next settlement deducts it. Never edit the paid entry.
  • Refunds go back to the wallet only, not to the original payment method (decision 4).
Done when

refunding twice is refused, the student's balance rises by the exact fee, and the institute's pending balance falls by the exact commission.

4.5

Real payment gateway: Razorpay

New; replaces the dummy card

NewP1
  • Replace the test card with Razorpay order creation and checkout. Remove the test card from the form, README and any seeded text before real students are onboarded.
  • Test and Live credentials are configurable, kept in .env or encrypted settings, and never sent to the browser.
  • Verify the payment signature on the server and confirm the paid amount equals the order amount before crediting the wallet.
  • Handle payment.captured and payment.failed webhooks idempotently, with unique constraints on the Razorpay order id and payment id, so a network retry never credits twice.
  • Never store card numbers or CVV.
Done when

a replayed webhook credits the wallet once, a tampered amount is rejected, and no card detail exists anywhere in the database or logs.

4.6

Payments list and reconciliation

NewP2
  • One screen lists gateway orders and payments next to the wallet credits they produced, filterable by status (Captured, Pending, Failed, Refunded), date range, student and institute.
  • Highlight mismatches: a captured payment with no wallet credit, and orders stuck in Pending. A "Verify with Razorpay" action lets Finance resolve them without editing the database.
  • Record gateway fee and GST on the fee per payment so the revenue view in section 8 can show net revenue.
Done when

a captured payment missing its credit is listed as a mismatch and can be fixed with one verified action.

5
Section 5

Commission and settlements

Each exam taken by an institute's student earns that institute a commission. The platform records it, tracks what is owed, and records the offline payments that settle it.

5.1

Default and per-institute commission

Built; New: refund and credit rules

BuiltNewP1
  • A global default rule, with an optional override per institute: a percentage of the effective fee, or a fixed rupee amount per exam, capped so commission never exceeds the fee.
  • The commission amount is calculated and locked on the exam record when the student is charged (decision 2), so later rate changes never alter earlier earnings or pending payouts.
  • On a refund or void the commission is reversed (4.4). Exams paid wholly from promotional credit earn no commission under the recommended default.
Done when

changing the rate next month leaves every earlier commission amount unchanged.

5.2

Due day, FIFO settlements and ledger

Built; New: reversal entries

BuiltNewP1
  • A configurable monthly due day (default the 7th): commission earned in a month is payable by that day of the next month.
  • Each recorded payout is applied to the oldest unpaid commission first (FIFO), giving Pending, Overdue and Next-due amounts per institute.
  • The ledger is chronological and shows every commission, refund reversal, clawback, payout (with mode and reference such as the bank UTR) and the running closing balance, which is what the platform owes the institute.
  • A payout cannot exceed the pending balance, and settlements for one institute are processed one at a time (row lock).
  • New ledger entry types: reversal for a refund and clawback for a refund of a commission that was already paid.
Done when

a ₹5,000 payout against ₹3,000 pending is refused, and the closing balance equals commissions minus payouts minus reversals.

5.3

Settlement statement PDF and monthly payout report

NewP4
  • Statement per institute and period: opening balance, itemized commissions, refund adjustments, payouts with bank or UPI reference, and closing balance, as a branded PDF.
  • Monthly payout register across all institutes, exportable to Excel and PDF, so Finance can review and release payouts in one batch.
Done when

the statement's closing balance matches the ledger for the same date.

5.4

Reverse or edit a settlement

NewP2
  • Only Owner and Finance. To undo a mistaken payout, create an offsetting reversal entry; the original row is never deleted.
  • A payout's non-financial details (UTR reference, notes) can be edited with a mandatory reason. Amounts and dates are changed only by reversal and re-entry.
  • Recalculate FIFO status and the closing balance after any reversal, and log actor, old and new values, reason and time in the audit log.
Done when

after a reversal the oldest commission shows as unpaid again and the ledger balance is correct.

5.5

GST, invoices and credit notes

NewP4
  • GST rate and tax-inclusive or tax-exclusive pricing are configurable, because the final treatment is confirmed with the Chartered Accountant (section 12).
  • Use the institute's saved GSTIN and state code to decide CGST plus SGST or IGST.
  • Generate sequential tax invoices for billed platform fees or top-ups, with no gaps in the number series per financial year, and a matching credit note for every full or partial refund. Both download as PDF.
Done when

invoice numbers are consecutive, and a refund produces a credit note that references the original invoice.

Section 6

Question and content management

Today every exam is generated live by one AI call and the model's own answer key is trusted. This section adds a managed question bank, automatic checks, human review, and student reports, so wrong keys are caught before students see them. How exams draw from this bank is decision 1.

6.1

Question bank

NewP3
  • A searchable list for Owner and Content reviewers: filter by training type, exam, syllabus board (State, CBSE, NCERT), subject, topic or lesson, difficulty (Easy, Medium, Hard), language (English, Telugu) and approval status. Search by keyword or question id.
  • Show each question's source (AI-generated or manual), times served in exams and student accuracy, with quick actions to edit, clone or retire a flawed question.
Done when

a reviewer can find a question by id or keyword, see how many times it was served and its accuracy, and retire it.

6.2

Review queue and second-pass answer check

NewP3
  • New AI questions go to a review queue. A reviewer sees the stem, options, correct answer, explanation and syllabus tag, then chooses Approve, Edit and approve, or Reject with feedback.
  • Before a question reaches a human, an automatic second pass solves it independently and flags answer-key mismatches and ambiguous options. Flagged items are highlighted for the reviewer. For maths and numeric physics the reviewer screen should show the computed check result where available.
  • Only approved questions can be served to students.
Done when

a question whose second-pass answer disagrees with its key is flagged, and an unapproved question cannot appear in any exam.

6.3

Reported questions and fix-and-regrade

NewP3
  • Students can report a question during or after an exam (wrong answer key, unclear wording, translation issue, out of syllabus). Reports collect in an inbox grouped by question with a count.
  • When a reviewer corrects a key or marks a question void or bonus, a one-click Fix and regrade recalculates the affected students' scores (including negative marking), updates reports and ranks, writes an audit entry, and can notify impacted students.
  • This depends on a rank feature, which must be built before ranks are regraded (see section 13).
Done when

correcting a key changes every affected exam's score once, and the change is in the audit log.

6.4

Syllabus manager

NewP3
  • Move the topic lists hardcoded in question_generator.py into database tables linked to training type, exam, syllabus board, subject and language. These tables also feed the institute profile lists in 2.4.
  • Owner and Content reviewers can add, rename, reorder, enable or disable topics and set topic weightage from the portal without a code deployment.
Done when

adding a topic in the portal makes it available to generation without any code change.

6.5

Syllabus upload per institute for RAG

NewP3
  • Approved lesson PDFs from Manage Syllabus (2.8) feed a retrieval-augmented generation pipeline: split into chunks, embed, and tag each chunk with institute id, exam, syllabus board, subject, lesson name and language.
  • During generation, retrieve the relevant chunks from that institute's approved lessons so questions follow its uploaded chapters rather than generic material.
  • Hosting note for the developer: shared hosting has no vector database. For a small number of chunks, store embeddings in MySQL and compare in Python; plan to move to a dedicated vector store if volume grows.
Done when

a question set generated for an institute cites chunks only from that institute's approved lessons.

6.6

Generation settings

NewP3
  • A settings screen for the model and temperature, questions per subject, difficulty mix (Easy, Medium, Hard), exam duration, marks per correct answer, and negative marking (for example 0, -0.25, -0.33 or -1).
  • Save presets per exam level (Basic, Intermediate, Advanced) or exam type, and snapshot the active rules onto every generated exam so later changes never alter old exams.
  • Negative marking changes how an exam is scored, so the scoring function must read the snapshot.
Done when

an exam keeps the marking rules it was created with after the settings change.

6.7

Streams, subjects and language

NewP3
  • Admins create and manage streams (MPC, BiPC with Botany, Zoology, Physics and Chemistry, MEC, General Studies) and custom subjects from the portal instead of a hardcoded list.
  • Questions and explanations can be generated, stored and served in English, Telugu, or side by side, following the institute or student language preference.
Done when

a new stream with its subjects can be created and used for generation without a code change.

6.8

Duplicate detection

NewP3
  • Before saving a generated or imported question, compare it with existing questions in the same subject or exam: first by normalized-text hash (exact duplicates), then by embedding similarity.
  • Block exact duplicates automatically; send near-duplicates (above roughly 85 to 90 percent similarity) to the review queue with a warning, so students do not meet repeated questions across practice tests.
Done when

submitting the same question twice stores it once, and a close paraphrase is flagged to the reviewer.

a test is invisible before its window, closes at the end time, and publishes ranks after it.
